# Gameplay spec

The canonical description of how the game behaves. Moved here from `CLAUDE.md` unchanged. Read the section a task touches; keep it in sync when behaviour changes. How the *code* is shaped is `docs/CODE_RULES.md`, not this file.

## Teams
- Fallen team is always team `#14`; Fallen itself cannot be claimed.
- New players get a personal team and one protected starting hex; every building in that hex (including Fallen ones) is wiped before the start schematic + core are placed.
- Eliminated players become Fallen; Fallen players can still chat and move their camera; Fallen can request teams via `/invite`.
- Team leaders are the players who created their teams.
- Personal team ids run 1..128 (14 is Fallen), which includes Mindustry's base teams. Team **6 is neoplastic**, the one team the game ships with `ignoreUnitCap = true` — and `Units.getCap` honours that flag before it checks the game mode, so it applies in PvP as well. `RulesApplier` clears it every rules pass; without that, whoever rolled id 6 played with no unit cap while everyone else was capped by their cores. (`TeamData.active()` also lets a neoplastic team with units but no cores/buildings count as active; harmless, since ownership and victory count real core blocks.) No other team has hard-coded rules — the other base teams appear only as colours.

## Captures
- Core dies → ownership changes logically immediately; buildings inside the captured hex are deleted immediately.
- Replacement Core Shard appears after 5 s; buildings created during those 5 s are deleted again right before replacement (double-wipe protection — preserve it).
- Captured cores become Core Shards. `/die` surrender restores Fallen Nucleus cores in surrendered hexes.
- Replacement cores are verified after placement; an unverified/missing core does not count as owned and cannot block victory as a phantom core.
- Victory, elimination and `/over` counts use actual existing core blocks; pending captures still count immediately for their pending owner.
- A core is matched to its hex by footprint, not exact origin tile (keeps the even-sized 4x4 Foundation tied to its hex after upgrades).

## Attrition
- Capture attrition: once on core capture, normal units within the 40-tile capture radius, tier-based values. Properties: `attrition.core.tier1To3Percent`, `attrition.core.tier4Percent`, `attrition.core.tier5Percent`.
- Range attrition: every 5 s, units ≥ 2 hexes from an owned core, same percent for all eligible tiers, default 20%. Properties: `attrition.range.percent`.
- Core-spawned player units never receive attrition; core units build/mine but deal no combat damage.
- Building-fired bullets deal 10% damage to buildings, normal damage to units.
- Both attrition settings persist across restarts.

## Player data (`config/evict-players.db`)
- Async writes on one background thread; profiles keyed by UUID; no IP addresses stored (the ban system reads Mindustry's admin store instead, which already keeps every IP per UUID). IP lookup for bans doesn't need them: console `playerinfo` resolves name/UUID via the plugin DB and prints last + all known IPs from Mindustry's built-in admin store (which already tracks every IP per UUID) — feed those to `ban ip`.
- Stored: last name, first/last seen, one total playtime, normal + ranked match counters, ELO/peak ELO; all observed names per UUID in `player_names`. Match stats exist only for normal and ranked matches — the main-lobby FFA round has no stats (legacy `ffa_*` / `ranked_playtime_ms` columns in old databases are ignored).
- Ranked wins/losses/played, ELO and peak ELO update only after a **Ranked** match (casual 1v1 never touches them); match rows store both players' before/after ELO.
- Normal wins/losses/played count every competitive `/play` match: casual 1v1, Teams and `/play` FFA (Random Teams records as Teams; Training/Sandbox never record). Ranked matches count only in the ranked counters. `/info` shows Total playtime, Normal, Ranked and ELO.
- Every `players` column newer than the original baseline has an `ALTER TABLE` guard, so databases created by old plugin versions upgrade in place instead of failing writes silently.
- One-time stats repair (tracked via `PRAGMA user_version`): pre-1.4 builds counted every casual 1v1 in the ranked counters, so on first startup the plugin recounts normal/ranked counters from the `duel_matches` rows and replays all ranked rows chronologically through `Elo`, rewriting each row's before/after ratings and every player's ELO/peak (manual `elo` values from before the repair are replaced).
- New players start at ELO 1000; peak ELO only ever rises (manual `elo` sets never lower it).
- Playtime flushes at round start, on leave and on shutdown; `/info` and `playerinfo` add live unpersisted session time.
- Playtime counts time on the match servers too. A worker has no database of its own: it reads the hub's (`../../config/evict-players.db`) so `/info`, `/top` and `/history` show real numbers on a match server, and it never writes. It publishes a running per-UUID total in `status.properties`; the hub diffs it every poll (~2 s) plus once more on worker exit and credits the growth, so a repeated or missed poll can neither double-count nor lose time. A reused worker folder's old status file is deleted at spawn so its totals cannot be credited twice.
- Lookup order for `/info [name]`, `playerinfo`, `elo`: partial latest-name match first; old names and UUIDs only if no latest-name match. Ambiguous `elo` names list candidates and change nothing.
- `/info` is public, never shows UUIDs to normal players — a server admin viewer additionally gets the subject's UUID (IPs stay console-only). No argument opens a clickable online-player picker; a name that matches exactly one stored player prints their stats, and a name matching several opens the same picker built from the matches (newest-seen first, capped, refine for the rest) instead of a text list.

## Commands
- `/fullassault` (`/fa`) — team-scoped toggle (never global), updates every 5 s, sends eligible unattended combat units to the nearest enemy core; ignores player-controlled units and units on mine/assist/rebuild/repair.
- `/invite [number]` — only the team leader accepts. When a team loses its final core, the team that destroyed the most of its cores claims it (tie → destroyer of the final core). Claimed players can join only their claimant's team.
- `/die` — leader-only surrender, available only after the round has run 10 minutes; before that it must not show a countdown. At 10 minutes a global status message lists active match player names only (no team/core counts, no mention of `/die`). No confirmation. Instantly destroys all team buildings/units, converts hexes to Fallen, restores Fallen Nucleus cores. If exactly one active personal team destroyed the most surrendered cores, players and claims transfer to it; otherwise claims are released.
- `/over` — ends a decided round early. Its own feature, unrelated to Extinction and to any clock: it is available for the whole round. Conditions: one team holds ≥ 50% of all cores, teams that never owned more than one core don't block it, teams that expanded must be fully eliminated. No confirmation. **Anyone may run it** once the conditions are met — the state of the map is as visible to a Fallen player or a newcomer as to the winner. A player on an active personal team asks about their own team, so they still get the "you need 2 more cores / you still need to eliminate X" answer; everyone else asks about whoever qualifies (`TeamManager.eligibleEarlyEndTeam()`, which declines rather than pick a winner in the impossible case of two eligible teams). Not available on a match server.
- Why anyone: it fixes a softlock. One team kills everything down to a single enemy core, that enemy leaves, and nothing can end the round — `checkVictory` won't fire because the neutral Fallen cores still count as an owner, so the map sits there until Extinction and everyone who joins waits it out. A start-core team that never captured anything doesn't block (the peak-cores rule), so `/over` is exactly the way out; before this, only someone on the dominant team could use it, and that player was usually gone too.
- Known and accepted: the blocker rule looks at a team's **peak** core count, so a team that expanded, got pushed back to one core and then left blocks `/over` for the rest of the round even though nobody is playing it. The peak rule is deliberate — it stops a real opponent being squeezed to one core and then `/over`-ed away instead of eliminated — and separating "pushed back" from "abandoned" would need per-team offline tracking. Left as is; Extinction ends that round.
- `/time` — round runtime since map start + the player's connected time since first join this round (join records remembered across startup scans; fallback is round start).
- `/help [page]` — paginated; aliases fold into their target's row (e.g. `/history (/h)`). The listed rows and their order are fixed in `Help.DISPLAY_ORDER` (`/t`, `/sync`, `/invite`, `/die`, `/over`, `/time`, `/play`, `/spectate`, `/fullassault`, `/history`, `/info`, `/top`, `/a`, `/ban`, `/free`, `/js`); a registered command that is not named there still shows up, after those rows, so nothing goes silently missing. `HIDDEN` drops `/help` itself and vanilla's `/votekick` + `/vote`, which are disabled on this server. Permission-gated commands such as `/ban` are listed and stay gated at execution. There is no separate dev help — former dev chat commands are console-only (`corecap`) or properties keys (attrition, walls).
- `/history` (`/h`) — a player's 1v1, Teams and FFA matches, most recent first.
- `/top` — the ranked ELO ladder (players with ≥ 1 ranked match), highest first; optional count (1–25, default 10). One command, no aliases.
- `/js <script>` — admin-only, the server console's `js` command in chat, one to one: the script goes to the same `Vars.mods.getScripts().runConsole(...)`. Only the output differs — the return value is sent to the admin who typed it and to nobody else, never to chat or the log. Registered on the hub and on a match server (a hub admin is an admin there via `AdminSync`). The script always runs on the main thread (posted, so it never runs on the thread that delivered the chat packet); `runConsole` never throws — a script error comes back as its text and is shown the same way. The result is escaped (`[` → `[[`, so `[1,2,3]` is not read as a colour tag) and cut at 700 characters. The script itself is written to the console log with the name that ran it before it runs — arbitrary code execution is worth an audit line — and the typed command is mirrored to Discord like any other. Listed in `/help`, gated at execution.

## Matches (`/play`, `/p`)
`/play` first asks **Extinction** | **Pure** (two buttons, one row). Extinction opens the game-mode menu below, unchanged; Pure is its own section further down.

Game-mode menu: `1v1`, `Ranked`, `Teams`, `Random Teams`, `FFA`, `Training`, `Sandbox`. (Hub side: `commands/Player` holds the `/play`, `/p`, `/spectate`, `/s` entries; `Matchmaking` is the mode menu and the solo start, `Challenges` the 1v1/Ranked flow, `MatchDrafts` + `MatchDraft` the Teams/Random Teams/FFA flow, `SpectateMenu` the `/s` menus on hub and worker; `MatchMode` is the mode list with each mode's rules as flags.)
- **1v1** — opponent picker (two per row, bottom cancel), accept/decline challenge menu. Casual: unranked `/history` entry (win/lose, no ELO), no ranked counters.
- **Ranked** — same flow as 1v1 but rated; the only ranked mode. Updates both players' ELO/peak ELO and ranked counters, stores a ranked `/history` entry with before/after ratings (recorded via `result.properties` on the hub). Behaves like a 1v1 on the worker.
- **Teams** — up to 8 rosters built purely via pick menus; challenger starts on Team 1; picks fill the current team. `Next team` (needs ≥ 1 player on the current team; hidden at the 8-team cap) and `Done` (empty trailing team dropped; ≥ 2 teams required). No player picked twice; uneven sizes allowed. Everyone gets an accept/decline invite; any decline or disconnect cancels for all. A team knocked out mid-match (3+ teams) is freed like an FFA loser. Stored unranked in `/history` (all rosters, win/lose).
- **Random Teams** — challenger picks team count (2-8), then picks a single player pool like FFA (≥ team-count players incl. challenger). After all accept, the pool shuffles into balanced teams (first teams get the extra player; sizes differ ≤ 1). Rosters not announced. Hub-only: launches as a regular `teams` match.
- **FFA** — pick any number of players (Done button), same invite flow, everyone on their own team. Knocked-out players become spectators: the match no longer waits for them, `/spectate` returns them to the lobby, and the hub lets them join the normal round (worker publishes an `out` list in `status.properties`). Stored unranked in `/history` (all participants, win/lose).
- **Training** — solo on a worker; nothing won/lost; `/die` ends it (no ELO) and returns to hub.
- **Sandbox** — Training + infinite resources; `/spectate` spectators may `/invite` to request joining, and anyone already in the match (owner or a previously promoted player) accepts with the normal leader `/invite` flow (spectator promoted to participant) — not just the original owner.

All modes run the same generated Evict map and worker rules: wait-for-everyone start gate, 5 s countdown, disconnect pause with rejoin window.

On workers, `/die` has no opening time limit: surrender works while waiting for players, during the opening countdown, and while paused (including an opponent's disconnect). A successful surrender cancels the pending start freeze/countdown and disconnect pause, hides their HUD, and resumes the game so elimination and return to the lobby can finish. Victory and solo session end also release any freeze. Sandbox keeps its owner-only `/die` rule.

`/spectate` (`/s`) lists each match as one button with two lines: the player names above, then `Extinction • <game mode>` or `Pure • <game mode> on <map>` below. This applies both on the hub and when switching between matches from a worker; the worker menu also offers Return to the lobby.

### Pure matches
Plain Mindustry PvP on a real map instead of the generated hex map. Pure menu: `Training`, `2 Team PvP`, `4 Team PvP`, `1v1 PvP` (modes `pure-training`, `pure-2team`, `pure-4team`, `pure-1v1` on the wire).
- **Maps** are the `.msav` files in `config/maps/` — every one of them except the Extinction map (`duel.worker.map`, `evict-map`). At hub startup `PureMaps` reads each map and counts the teams owning at least one core (teams, not cores; derelict does not count; the console prints the list). 2-team maps serve 2 Team PvP and 1v1 PvP, 4-team maps serve 4 Team PvP, Training may use any; other counts are ignored. Maps are copied into every worker folder at each spawn, so a map dropped into the hub's `config/maps` is playable after the next hub restart. Because the server's own map shuffle would otherwise rotate the hub's next round onto a Pure map (and generate it at that map's size), the hub's next map is pinned to the Extinction map; the console `nextmap` override still wins.
- **Rules**: vanilla. The worker turns generation off (`oregen auto off`) and hosts the chosen map with `host <map> pvp`: no hex rules, no attrition, no capture, no Extinction, no banned blocks, and none of the Extinction damage tweaks (turret building damage, harmless core units) — those are applied only on non-Pure processes. Server-wide things stay: bans, word filter, lock, chat routing, admin sync. Vanilla's `pvpAutoPause` is switched off; the referee's own gate and disconnect pause run instead. Vanilla's PvP game over decides the winner (`GameOverEvent` → the referee); vanilla then still shows its own "team is victorious / next map" screen and would reload the map after `roundExtraTime`, by which time the players are back on the hub and the worker has closed — a second `PlayEvent` never restarts the referee.
- **Nothing is recorded**: no ELO, no `/history`, no ranked counters. The Discord start/end embeds, hub announcement and Discord status say e.g. `Pure 2 Team PvP on <map>`; the `/s` list puts `Pure • 2 Team PvP on <map>` below the player names.
- **`/maps`** (listed in `/help`; hub only; match servers say to use the hub): your own Pure map list, one scrollable menu with every map and its team count, no pages. Selected maps come first in normal colour; deselected maps are scarlet at the bottom. Tap any map to toggle and redraw. Deselections are account vetoes, saved across restarts in `config/evict-map-vetoes.properties` (`uuid` -> comma-separated map names) through `PropertiesFile`, never the player DB. New maps are selected by default.
- **Flow**: players first, map second, invites last. The Pure map picker is one scrollable menu with one map per row and Cancel at the bottom, filtered to the mode's team count. Every participant's vetoes apply (only the challenger for Training): vetoed maps are excluded from selection but shown scarlet at the bottom. Tapping a vetoed map cannot select it. If no map remains, the picker says so and cancels the setup. Vetoes are checked again when choosing the map and before launch, so a veto changed during an invite cannot be bypassed.
  - **Training**: any map; solo; the challenger is placed on the map's first core team (lowest team id), the other cores stay as they are. `/die` ends it and returns to the hub; destroying every other core ends it too ("Game over." in the embed).
  - **1v1 PvP**: pick the opponent, then a 2-team map with both players' vetoes applied, then accept/decline. The invite names the map ("… challenged you to a Pure 1v1 PvP on <map>").
  - **2 Team PvP**: a roster grid (`PureRoster`): two columns side by side, Team 1 left, three rows to start. The challenger is fixed in Team 1's first slot. Every empty slot is a `+`; clicking it opens the online-player picker for that column; clicking a name removes that player. A new row appears once any column is full, up to 20 per team; uneven sizes allowed. `Done - pick map` needs at least one player in every team, then opens the 2-team map picker with everyone's vetoes. Choosing a map sends the usual accept/decline invites naming that map (one decline, one leave or one timeout cancels for all).
  - **4 Team PvP**: the same with four columns and 4-team maps. A team that loses its last core is out: its players are demoted to spectators (`/s` returns them to the lobby, the hub lets them join the round), and their leaving no longer pauses the match.
- **On the worker**: roster *i* plays as the map's *i*-th core team in team-id order (`PureMatch`); every join or rejoin of a participant puts them back on their roster's team. `/die` in a Pure PvP match surrenders: the player's team loses all its cores (announced), vanilla decides the rest. Start gate, countdown, disconnect pause, `/s`, self-exit, status and result files are the normal worker infrastructure.

Chat routing (workers only): every mode except **Ranked** uses normal global chat for everyone. In a **Ranked** match only the two duelists chat on global; viewers and casting admins have their normal chat routed to the spectators' chat instead (so nobody can leak information to the players). A casting admin (a server admin; the hub syncs its admins into every worker, see `AdminSync`) reaches global with an inverted `/t`: their normal chat goes to spectators, and `/t` broadcasts to everyone. Plain viewers have no path to global. The hub's `/t` is left vanilla; the worker overrides `/t` for this.

Worker infrastructure (worker side: `Referee` — roster, joins/leaves, victory, surrender, result; `StartGate` — join freeze, camera settle, countdown; `DisconnectPause` — rejoin budgets, rejoin HUD, build-plan guard; `Sandbox` — owner and guests; `WorkerExit` — return to hub, `/s` hop to a sibling, self-exit; `WorkerStatus` — `status.properties` and the sibling scan; `MatchHandshake` / `MatchResult` — the two files; `MatchChat` — the Ranked chat routing and `/t`):
- One Mindustry process hosts one game, so each match gets its own worker process — spawned on demand, never idle.
- Handshake `duel.properties` (hub → worker, `MatchHandshake`): `mode`, `label`, `team.count`, `team.N` UUID lists, `name.<uuid>`, `hub.ip`, `hub.port`. Result `result.properties` (worker → hub, `MatchResult`): `mode`, `winner.uuid(s)`, `loser.uuid(s)`, `reason`. Chat `chat.log` (worker → hub, append-only): the worker's captured chat/command/join/leave lines for the Discord chat mirror, tailed by the hub and deleted at spawn (see Discord chat mirror). Status `status.properties` (worker → hub, rewritten every **1 s**): state, game time, connected players, `out`/`participants`/`owner`, `playtime` (`uuid:millis` running totals), `banrequests` (accounts banned on the worker, for the hub to apply) and one `banrequest.<uuid>.actor|time` block per request, plus `source|word|text` when the word filter decided it — so the hub's ban log can name who banned and point at this worker's console log. The hub polls those files once a second (`ADVERTISED_COUNT_REFRESH_MILLIS`), which is the one poll carrying chat, playtime and ban requests across. Only `ranked` results record as ranked; `1v1`/`teams`/`ffa` become unranked `/history` entries; Training/Sandbox are never recorded.
- On accept, `Matches` (the hub's worker pool) reserves a free port (a `MatchSlot`), `WorkerFolder` provisions `duel-workers/duel-<port>/` from the hub's jar + `config/mods` + `config/maps` if missing, writes the handshake, launches `java -Devict.duelWorker=true -jar <jar>`, injects `config port` and `host` over stdin, polls the port, then `Matches` redirects players with `Call.connect`. Spawning/readiness wait run on a background thread; redirects and slot bookkeeping on the main thread. `WorkerReports` is the worker→hub side: the status poll (players, playtime, ban requests, chat lines) and the result file (log line, `/history`, Discord end embed).
- Worker self-exits when empty (frees the hub slot) via a plain `System.exit(0)`; backstops: startup grace (no player ever arrived), 110-min max lifetime, JVM shutdown hook. A close from a decided match (win/lose or solo `/die`, which already sent everyone back with their own 5 s message) exits straight away. An abandoned worker still being watched instead counts down out loud first: a per-second ticking HUD popup (restart-countdown style) for 5 s, then a 3 s hold at zero, then it exits. The countdown ticks on the real-time scheduler (not `Time.run`) so it still runs when the match sits in an unresumed disconnect pause.
- Up to `maxWorkers` matches at once (1-10); all busy → `/play` says try again shortly. A blank duel-server IP leaves `/play` inert. Closing menus / losing the opponent cancels cleanly; stale challenges drop on leave.
- Remote players need the whole worker port range forwarded.

## Extinction
`gameplay/WaveExtinction` — one continuous wave that eats the map from the outside in, tile by tile. It replaced the ring collapse (`ExtinctionManager`, deleted in 1.9.4) and inherited its schedule, its win conditions and its scope unchanged; only the pacing is different. Round-clock driven on hub and match server alike — **there is no command that starts it** (the 1.9.2/1.9.3 test switch `/extinction` is gone).
- Timer starts when the generated round starts. `01:20:00` global 10-min warning; `01:25:00` 5-min warning; `01:29:00` 1-min warning; `01:30:00` `[scarlet]Extinction has begun.[]` and the wave arms itself over **600 s**, so the map is gone by `01:40:00` — the same window the five rings were spread across. Warnings fire one per tick, so a server that comes up mid-round past several of them announces them in quick succession rather than swallowing what it missed.
- **The center hex is never touched**: it is the prize. A hex is marked extinct (owner → derelict, captures suppressed) just before the wave reaches its core, so a core lost to the wave is not treated as a capture. Units beyond the front are killed once a second.
- **How a round ends.** Marking a hex extinct is what takes it out of the ownership counts (`TeamManager` skips extinct slots), so each batch that killed at least one hex re-runs the two checks the rings ran: `eliminateCorelessTeamsThroughExtinction()` then `checkVictory()`. If all surviving cores belong to one team, that team wins immediately. In practice the round is decided when the last hex besides the center goes — whoever holds the center core then, **including Fallen** (which resets the round normally) and including no core at all (Fallen). `finish()` hands that holder to `TeamManager.finishExtinction` as the backstop for the cases victory checking does not cover. Conversion stops the moment the round ends; the map is about to be replaced anyway.
- **Why a wave.** Each converted tile costs two reliable packets to *every* client (`removeNet` + `setFloorNet`, ~18 B per client), and `Net.send` skips no connection — not even one still receiving the world. The ring collapse drained a whole ring at 128 tiles per **tick**, i.e. ~135 KB/s per client at 60 TPS, against the 32 KB per-client write buffer `ArcNetProvider` allocates (`new Server(32768, 16384, …)`). An overflow is not queued, it is a disconnect (`ArcConnection.send` → "Error sending packet. Disconnecting invalid client!"), which is why a ring collapse on a lagging server dropped nearly everyone at once — and why a player joining during one never finished the world stream and got *Failed to load world data!* (a 30 s client-side connect timeout, `NetClient.update`, `@disconnect.data`).
- **Same work, different pacing.** The same ~262,000 tiles are converted either way. The rings did it in five bursts inside a 10-minute window they otherwise spent idle (~6 % duty cycle); the wave spreads the identical work evenly: **~445 tiles/s, ~7.8 KB/s per client, factor ~17 lower peak, same end time**. The write buffer goes from 0.24 s of headroom to 4.1 s.
- **Time-based, not tick-based.** The batch comes from elapsed wall-clock time, so a TPS drop cannot stretch the collapse: ~7 tiles/tick at 60 TPS, ~44 at 10 TPS, identical packets per second. `MAX_TILES_PER_TICK` (455 ≈ ¼ of the write buffer) caps a catch-up burst; at this duration it only engages below ~1 TPS. (Wall-clock, not round time, because the constraint being paced is network load — a duel's disconnect pause does not pause the wave.)
- **Equal area, not equal radius.** Tiles are consumed farthest-first from a distance-ordered list (counting sort over integer distance), so the tile rate stays flat no matter how much hex area sits at a given radius. A linear radius would idle at the corners and then burst 120× harder mid-map.
- **Scope.** Only the hex circles, same membership test the rings used (nearest slot owns the tile, within `HexGrid.HEX_RADIUS`) — gaps between hexes and filled wall hexes stay. `removeNet` is skipped for tiles carrying no block, which halves the packets again.
- The center hex + its six neighbours are still protected from procedural filling at generation time, so the prize always exists.
- The `extinction.terrainChangesPerTick` setting is loaded by `EvictSettings` and read by nothing — it does nothing, and did nothing under the rings either.

## Bans
Hub-only decision making; workers apply what the hub decided.
- Every ban path is widened, and admins keep using the ones they know: `ban id`, `ban name`, `ban ip` and the in-game hammer all fire Mindustry's own `PlayerBanEvent`/`PlayerIpBanEvent`, which `BanManager` hooks. Vanilla alone is much narrower — `ban id` never touches the address, `ban name` short-circuits before it, `ban ip` misses the accounts' other addresses.
- The widening is **one step and stops** (1.6.0; the old two-step cascade banned strangers through shared addresses — CGNAT, VPN endpoints, university networks — and one more hop through their dynamic IPs turned one ban into hundreds). Seeded with a UUID: that account plus its own recorded IPs — never onward through those IPs to other accounts. Seeded with an IP: the address plus the accounts seen there (the set vanilla's `banPlayerIP` flips anyway), and nothing beyond them.
- Plugin-added addresses go straight onto the banned-IP list, **not** through `banPlayerIP` — vanilla's method permanently UUID-bans every account that ever used the address, exactly the shared-address disaster the one-step rule exists to avoid. A quietly added address blocks connections and is still lifted by a normal `unban` (vanilla drops the account's addresses from the same list). Only an admin's own explicit `ban ip` keeps vanilla's account-flipping semantics.
- `/ban [name]` — admin-only chat command with the `/info` UX: no argument opens a picker of the online players (never the admin themself); a name searches the stored players (partial latest-name first, so it works on someone who already left), several matches open the picker. Always a named confirmation menu before anything happens. It only hands the account over, so it is widened, kicked, synced, announced and logged like every other path. It works on a match server too: there the ban takes effect locally at once and is forwarded to the hub (see below). Listed in `/help`, gated at execution.
- `banplayer <name/uuid>` — console ban for an offender found in the chat log after they left: resolves against the plugin DB like `playerinfo` (vanilla `ban name` only works on connected players); an ambiguous name lists candidates and bans nobody.
- Everything the widening catches is banned, and every affected player online is kicked immediately, on the hub and inside running matches (an IP hit kicks the connection even when the account itself is not banned).
- **Bans made on a match server are forwarded to the hub** (`BanForwarder`): the local ban kicks the player out of the match at once, and the account plus its story (who banned, the worker's console time, the word filter's evidence if it was the filter) travels in `status.properties`; the hub applies it on its next poll (~2 s) through the normal path. Without this a worker ban only lived in that worker's throwaway admin store, was lifted again by the next ban-list sync, and the player walked straight back onto the hub — nothing widened, nothing synced, nothing logged. Bans that `BanSync` itself applies are ignored (they came from the hub). An address ban typed into a worker console is *not* forwarded — it only warns, address bans belong on the hub.
- Every ban the hub applies is **announced in the hub chat**: `<name> was banned.` / `… was banned on a match server.` / `… was banned automatically for using a forbidden word.` Names only — never an address (an `ban ip` announces the account it hit, or stays silent if it hit none), never UUIDs, never the offending text. Imports and unbans are silent.
- **Ban screen** (`BanScreen`, 1.11.1): what a banned player reads, on the hub and on a match server alike. Vanilla's `KickReason.banned` is a fixed enum the client translates itself ("You are banned on this server."), with no room for an invite; so every ban kick the plugin makes (`BanManager`, `BanSync`, `BanForwarder`, the word filter's own reason) kicks with a **string** instead: `You are banned from this server.` plus, when `moderation.banAppealUrl` is set, `To appeal, join our Discord: discord.gg/<code>`. The kick dialog is a plain label — nothing in it is clickable or copyable — so a `discord.com/invite/…` URL is shown in its short `discord.gg/…` form for typing by hand. The second screen is the one that matters: a banned player who comes back is refused inside vanilla's connect handlers, but in v157.4 `ConnectionEvent` fires before the address check and `ConnectPacketEvent` before the account check, and `NetConnection.kick` is a no-op on a connection already kicked — so `BanScreen` looks the ban up itself on those two events and kicks first with the appeal text, and vanilla's `kick(KickReason.banned)` a few lines later does nothing. Same ordering at ban time: `banPlayerID` fires its event synchronously, the plugin kicks inside it, vanilla's own kick after the ban is the no-op. Set as `moderation.banAppealUrl` in the properties file. The setting is copied into workers with the rest of the settings file (it is not a `discord.*` key), so a match server shows the same screen from its next spawn.
- Unbans are **not** cascaded — `unban` behaves exactly as Mindustry applies it (which does drop the account's IPs from the ban list). They are logged, nothing more.
- `config/evict-bans.txt` is rewritten from the live admin store on every change (`uuid <id>` / `ip <addr>` lines, written via a temp file + move so a worker never reads a half-written list). Workers read it from `../../config/`, hand it to their own admin store every 5 s and kick anyone it now covers — without this a banned player could join a match server directly on its port. A worker never bans anything of its own accord; entries the hub has dropped are lifted again. The one-step rule holds on the worker too (1.9.1): a synced address goes straight onto the banned-IP list, **not** through `banPlayerIP` — that vanilla method flips every locally known account that has ever used the address, so before the fix one shared address (CGNAT, VPN, household) permanently banned bystanders on whichever worker they happened to have played on, invisibly to the hub, and the sync then held them banned forever through the very address that branded them. An account stays banned on a worker only when the hub lists it **by UUID**; sharing an address with a banned account is not enough. A worker started on the fixed build repairs a store poisoned by an older one on its first sync.
- Pre-existing bans are pulled through the cascade **once ever**, on the first hub start after upgrading (`moderation.banBackfillDone`); seeds already covered by an earlier cascade in the same run are skipped. That automatic run necessarily happens before a log webhook can be configured, so it widens the bans but writes nothing up.
- Ban log: `banlog <url>` posts a new message per action into its own channel — never an edit, a log is a sequence. One embed with all names, all UUIDs, all IPs the action covered. Every ban that knows its story adds `Banned by` (admin name, `the console`, or `the word filter`), `Server` (`the hub` or `match server on port <n>`) and `Console time` in the server's own log format (`MM-dd-yyyy HH:mm:ss`) — so the incident can be found again by searching that server's log. A word-filter ban is its own entry (orange, `🤖 Word filter ban`) and adds, above those, the word that tripped, whether it stood in the **chat message** or the **player name**, and the offending text itself (the whole chat message, or the name). The VPN scan's one-liners (see VPN scan) and the lock's `🔒 Locked` / `🔓 Freed` lines (see VPN lock) go into the same channel through the same queue, so they can never crowd a real entry out of order. **Staff-only channel**: it publishes addresses. Messages are queued and released one per 1.5 s (Discord rate limits a webhook at a handful of requests a second); an import of more than 25 old bans collapses into summary embeds of 20 instead of flooding the channel.

## Discord commands
`/ban <uuid|ip>`, `/unban <uuid|ip>` and `/free <uuid>` as Discord slash commands, for staff who are not at the console. Hub-only, like every other moderation path. `/free` frees a locked account (see VPN lock) through the same `PlayerLock.free` the in-game and console commands use, and answers with the same line.
- **Nothing is decided in Discord.** A UUID goes through the same `BanRequest` an in-game `/ban` produces; an address goes through the same `banPlayerIP` a console `ban ip` calls. So both are widened one step, kicked, written to the workers' ban list, announced in the hub chat and **posted to the ban log automatically** — because they took the ordinary route, not because the Discord layer arranged it. The log entry names the person: `Banned by <their Discord name> (Discord)`, `Server: the hub`. Unbans are not cascaded, exactly as elsewhere.
- **The reply is ephemeral** (`flags: 64`) — only the admin who ran the command sees it, and it leaves no message in the channel: `Name (uuid) was banned from the server.` / `… was unbanned from the server.`, or the bare address for an IP, or the bare UUID for an account the server has never seen. Already banned / not banned / a blank argument each say so and change nothing. The whole line is markdown-escaped: it carries a player-chosen name.
- **UUID or IP only**, told apart by looking for a dot or a colon (a Mindustry UUID is base64 and can hold neither). Deliberately no name lookup — a name is ambiguous and an ambiguous ban is the wrong kind of surprise; use console `playerinfo` to get the UUID.
- **Two permission layers, and the second is the one that matters.** `default_member_permissions: BAN_MEMBERS` hides the commands from ordinary members, but anyone administering that Discord server can re-open them in Server Settings → Integrations without the game server hearing about it. So every interaction is checked again on arrival, against the configured server id **and** role (`discord.commands.guild` / `discord.commands.role`) taken from the payload Discord signed. No role configured → only a member holding Discord's own Administrator permission, so the commands are never open to everyone by accident. A refusal is logged to the console with the name that tried.
- **The gateway** (`DiscordGateway`) is the plugin's only inbound Discord connection, and exists solely because receiving needs one: Discord delivers an interaction either to a public HTTPS endpoint of your own (a certificate, a reverse proxy and an open port in front of a game server) or over this outbound WebSocket. Not a Discord library — four opcodes, `intents: 0`, so the bot never asks to see messages or members. Heartbeat with zombie detection, resume, reconnect with backoff. Every frame and every piece of its state belongs to one scheduler thread; each connection carries a serial so a dying socket cannot tear down its replacement.
- **Answering is two steps** (`DiscordCommandApi`): Discord drops an interaction not acknowledged within 3 s, and the ban has to be posted to the main thread and waited for, so the ephemeral acknowledgement goes out first and the real answer edits it. Guild commands, not global — usable the moment they are registered instead of up to an hour later.
- **Same bot as the chat mirror**, same `DISCORD_CHAT_BOT_TOKEN` in `config/evict.env` — one credential to rotate rather than two. It must be invited with the **`applications.commands` scope** as well as `bot`, or registration fails with HTTP 403. `discord.*` keys are stripped from worker configs as usual, and the token is never copied into a worker.
- **Setup asks Discord, not the admin.** The bot is already in the Discord server, so the server id is something it can look up rather than something to copy: `discordcommands setup` takes no arguments, and roles are chosen by name. `chatlog setup <server-id>` also wires the commands to that same server in passing — the two features share a bot and a Discord server, so typing the id twice was pure friction. The token is read at startup whether or not anything is wired up yet, so the checklist never reports a token that is sitting in the file as missing.

## Word filter
Automatic ban for a hard-coded word list, in chat or in a player's name. Swearing is not the target.
- `src/Extinction/BannedWords.java` holds the list: `WORDS` (banned anywhere, also inside a longer word), `WHOLE_WORDS` (only as a word of its own, for entries that are a normal part of harmless words — `negr` is Montenegro, `nazi` is nazionale and the name Nazir), `NAMES` (banned in a player's **name** only — joining with it is an automatic ban, the same text in chat passes; for impersonation, advertising, or a word that is fine to talk about but not to be called), `ALLOWED` (harmless words containing a banned one, cut out before the scan). Edit and rebuild; nothing else.
- A name is held to the stricter list: `WORDS` + `WHOLE_WORDS` + `NAMES`. Chat is checked against `WORDS` + `WHOLE_WORDS` only. `NAMES` entries match anywhere in the name like `WORDS`, through the same folding, and `ALLOWED` cuts out of them the same way. The ban itself is identical either way — same reason, same log entry marked `player name`, same evidence.
- One plain lowercase entry covers every disguise: `WordFilter` folds colour tags, accents, invisible characters, Cyrillic/Greek lookalikes and leetspeak away, then matches a per-entry pattern where each letter repeats (`niiigger`) — so the entry needs the right *distinct* letters, and Niger with its one `g` is not `nigger`.
- Separators between letters (`n i g g e r`) only for entries of 5+ letters; on a short entry that allowance bans ordinary sentences. `ALLOWED` is matched strictly (letters exactly, adjacent, once) so an allowance cannot be widened into a way through.
- Chat hits drop the message as well as banning, so the filter registers before every other chat filter. Names are checked on `PlayerJoin`.
- The hub bans through `banPlayerID` — widened, kicked, synced, announced and logged like an admin's, but the ban log entry is marked as the filter's and carries the word, where it stood (chat message vs. player name), the offending text and the console timestamp (see Bans). A worker bans locally (the player is gone at once, kicked with the filter's reason before the ban) and forwards the account plus that same detail to the hub in `status.properties` (`banrequests` + `banrequest.<uuid>.actor|time|source|word|text`), which applies and logs it against the worker's port and its console time.
- The console line is written before the ban and quotes the text, so the log and the Discord entry name the same moment.
- Test a new entry with `wordfilter test <text>` before trusting it.

## VPN scan
`moderation/vpn/VpnScan` (1.12.0; second source 1.12.1). The scan itself is a measurement: it writes every flagged join down and decides nothing. What is decided on it — a first join through a VPN is held for an admin — is the lock, its own section below (1.13.0).
- **The gap it measures.** The cascade covers a banned player who comes back with the same UUID from a new address (UUID ban) or with a new UUID from the same address (the account's addresses were banned with it). It cannot cover a new UUID from a new address — and for that the evader needs a VPN. So the VPN is not *a* trait of the evader, it is *the* trait the ban system cannot see, and before anything is done about it the plugin writes down who actually arrives through one: the evaders, and every regular who simply likes their privacy.
- **Two sources, asked side by side, because one database is not enough.** The first address that slipped through (`135.106.24.229`, a proxy in an "IT Hostline Ltd" hosting range) is *clean* at vpnapi.io and `proxy` + `hosting` at ip-api.com. So every join is looked up at both — [vpnapi.io](https://vpnapi.io) (`GET /api/<ip>?key=…`; flags `vpn`, `proxy`, `tor`, `relay` = Apple's iCloud Private Relay, listed so it can be told apart; needs the key) and [ip-api.com](https://ip-api.com) (`GET http://ip-api.com/json/<ip>?fields=…`; flags `proxy`, `hosting` = a data-centre range, where every VPN exit lives whether or not a database knows the provider's name — and where a cloud-gaming box lives too, which is why the line names the flag; `mobile` = a cellular address, **written down but never a hit**, because that is the one an address-based check can never pin and how often it occurs is part of the evidence; no key, free tier is plain HTTP, 45 lookups a minute, non-commercial). A hit is a hit from **any** source; the line says what each one answered (`vpnapi: clean / ip-api: proxy, hosting`), and a source that could not answer is simply absent from it. Without a vpnapi key the scan runs on ip-api alone and says so at startup.
- **What happens on a join (hub only).** A hit is written as one console line and one line in the ban-log channel: name, UUID, address, what each source said, the network behind it (ASN, organisation, country — the reader's second opinion: an "M247 Europe SRL" is a VPN exit, a flagged "Deutsche Telekom AG" deserves a doubt) and **the account's age**: first seen (from the plugin DB, `not stored yet` for a brand-new account), total playtime and Mindustry's own join count. The age is the point — the planned rule is "lock new accounts on a VPN, let known ones through", and the threshold for "new" has to come from these lines, not from a guess. A clean address writes nothing. Every flagged join is written down, also the tenth of the same account from the same address (the hub sees a couple of hundred joins a day at most, and a player who keeps reconnecting is itself worth seeing) — the cache only saves the lookup, never the line. Everyone arrives at the hub first and an unrostered joiner on a match server is a spectator anyway, so workers run none of it.
- **Cost control**, because both services count requests: one lookup per *address*, the combined verdict remembered for 24 h in `config/evict-vpn-cache.properties` (so a restart does not spend the day over, and the same regulars' evenings cost nothing after the first) — a remembered verdict that lacks a source which could answer now (written before that source existed, or while the vpnapi key was missing) does not count as remembered; per-source caps (vpnapi 900 per UTC day, the free tier being 1000; ip-api 40 a minute against its 45); a pause when a service answers 429 (an hour for vpnapi, whose allowance is daily; a minute for ip-api); at most 50 lookups in flight so a join flood cannot queue a hundred requests; loopback/LAN addresses never asked about. Each source runs on its own daemon thread and hands its answer back on the main thread — every piece of the scan's state is main-thread only, and a failure is a value (`IpLookupResult`), never an exception on the game loop. **Every one of those fails open**: a join that cannot be looked up is a join that is not written down, never one that is refused; a source that fails leaves the other's answer standing. A rejected key (401/403) stops asking vpnapi until `vpn reload`; a service outage logs one warning a minute per source, not one per join.
- **The key** is `VPNAPI_KEY` in `config/evict.env` (see Secrets file), optional since 1.12.1 (ip-api needs none). An existing `evict.env` predates the key, so it has to be added by hand — the console checklist says exactly that, and `vpn test <ip>` spends one lookup per source to prove it: what each source answered is printed in the console **and** posted into the ban-log channel marked as a test, so one command shows that the keys and the channel all work before the first real join is written there. Never copied into a worker, never typed into a command.
- Every join is still written down when flagged, whether or not the lock takes it — a locked join gets the lock's own line instead of the scan's (see VPN lock).

## VPN lock
`moderation/lock/PlayerLock` + `moderation/lock/LockGate` (1.13.0; prefetch, automatic free, padlock marks 1.13.1). An account's **first join** through a VPN, proxy or hosting range is **locked** until an admin frees it — or until it comes back from a clean address. Not a kick and not a ban: the player is in, can look around, read the chat and watch matches — and cannot do anything else. The idea is Vinny's: an evader is stopped, and a real newcomer sees people who will let them in rather than a closed door.
- **Who.** Only a *first* join (Mindustry's own `timesJoined` for the account is 1 when the join event fires) that the scan flags. A known account on a VPN is a regular who likes their privacy and is only written down; an account an admin freed is **verified** and never held again. `moderation.vpnLock` (default on; `vpn lock off` turns the decision off — accounts already locked stay locked until freed).
- **Automatic free.** A locked account that joins again from a *clean* address (no source flags it) is freed on the spot, by the gate, without an admin: the evader's clean address is his real one, which the ban cascade already knows, so this exit is open to the newcomer who turned their VPN off and closed to the evader. An automatic free does **not** verify — the account is scanned like any other from then on (a first join it can no longer be, so it cannot be locked again either); the free line names `a clean address (automatic)`. No verdict (services down) keeps the lock.
- **At the door** (`LockGate`, hub only). The lookup is started the moment the connection opens (`ConnectionEvent` → `VpnScan.prefetch`, address known, UUID not yet), while the client is still downloading the world; by the time `PlayerJoin` fires the verdict is normally in the cache and the decision is instant — a newcomer gets their hex with no delay at all. The join and the prefetch share one request (`VpnScan` coalesces lookups per address). When the verdict is still out at join time, the first join is parked on the Fallen team without a hex (`TeamManager.assignLocked`) for **at most half a second** and then onboarded anyway (`TeamManager.releaseLocked`: personal team + hex) — a newcomer must not wait for their hex; a verdict that arrives later and says VPN still locks the account, parking them again and leaving the hex behind as an unattended team, like a player who left. No verdict at all (both services down, allowances spent) **fails open**. A player who leaves in between is locked all the same; the lock is on the account, not the connection. A round reset never hands a locked or held account a hex: the connected-player scan parks them again (`assignConnectedPlayers(spectator, locked)`).
- **What a locked account can do** (`PlayerLock`, enforced on the hub **and** on every match server): watch, read the chat, use `/s` (`/spectate`, `/sync`). Every chat line — global and `/t`, both go through `admins.filterMessage` — is dropped and answered with the reminder; every other command is answered with the reminder too (`LockCommandGate`, a delegating wrapper installed as `netServer.clientCommands`, the one place every command passes whether vanilla, this plugin's or another's; a refused command returns `valid` so the text is neither treated as chat nor followed by "unknown command"); every build plan, break, rotate, configure, item, unit or turret control, payload and ping is refused by an action filter — everything but `respawn`, which they need to fly at all. The unit flies at a **tenth** of its speed: four vanilla status effects stacked (`slow` 0.4 × `freezing` 0.6 × `tarred` 0.6 × `sapped` 0.7 = 0.10) plus `disarmed`, refreshed every second; vanilla ones because clients install nothing and a status they do not have would break their unit sync — the icons on the unit are the honest side effect. A locked account is on the Fallen team (it has cores to spawn at), is never offered in a `/play` picker (an invite is a menu, which the command gate cannot refuse, and a locked account rostered into a Teams match would sit in it mute), and its chat attempts still reach the Discord mirror **marked with a padlock** (`🔒 Name: text`, joins and leaves too — `ChatLogCapture.setLockMarker`) so a "please free me" is told apart from the chat around it. **In game a locked player is marked too**: `PlayerLock.NAME_PREFIX` — the game's own padlock glyph (`Iconc.lock`) in red — is put in front of `player.name`, which the game syncs to every client, so the player list and the nameplate show it; it comes off at the free, is stripped everywhere the plain name is wanted (`PlayerLock.stripPrefix`: the lock entry, the log lines, the mirror), and never reaches the player database (which records the name at join, before the gate runs, and reuses that at leave). A worker puts the prefix on and takes it off by following the list, so a free on the hub reaches a locked player watching a match within seconds. On join and on every refused message: `Your account is locked. It is new and joined through a VPN or proxy … To get freed, join our Discord discord.gg/<code> and ask an admin.` — the invite is `moderation.banAppealUrl` again; a join also gets it as a dialog.
- **Freeing**: `/free [name]` in-game (admin; `/ban`'s picker UX over the locked accounts, always a confirmation), `free <name/uuid>` on the console (no argument lists them), `/free <uuid>` in Discord (same bot and permission check as `/ban`; the UUID is in the lock line). All three go through `PlayerLock.free`: the account leaves the lock list, is written to the verified list, a freed player who is online gets their team and hex at once, and the ban log gets the free line. Only the hub frees; a worker's `/free` says so.
- **The list** is `config/evict-locks.txt` (`locked <uuid> <since> <ip> <reason> <name>` / `verified <uuid> <since> <name>`, tab-separated, written through a temp file), read back by every worker from `../../config/` every 5 s by modification time — the ban list's arrangement — so a locked player who `/s`-hops into a match cannot talk there either. A worker never locks or frees.
- **Staff see it**: one `🔒 Locked` line in the ban-log channel (name, UUID in a code span for `/free`, address, what each source said, the network) and one `🔓 Freed` line; online admins get a chat line at the moment of the lock; the console logs both.
- **Known limits, recorded on purpose:** the lock only takes *first* joins, so the group's *existing* accounts are untouched until they are banned and come back fresh; mobile carriers hand out a new address every few minutes and are no VPN, so no address-based check catches a hotspot, and a subnet or ASN graylist is only ever acceptable as a temporary admin lever *because* its consequence would be a wait, never a ban. A locked player still occupies a slot; nothing kicks them for idling.

## Client message ids
Some modified clients defeat Mindustry's "same message twice" rejection by appending a two-character id, built by their `InvisibleCharCoder` from `U+0F80..U+107F`, to every chat message — `hello` arrives as `helloၬ࿻`. `core/util/MessageIdFilter` cuts it out of **console output only**; the network message is passed on untouched, because those clients use the id among themselves and stripping it would break them.
- Exactly the **last two** characters, and only if **both** are in range — a matching character anywhere else in the message stays, so a Tibetan or Burmese sentence keeps every character it had. A message that ends in two such characters for real loses them; the alternative is leaving the noise in every line.
- Installed by wrapping `Log.formatter`, first thing in `bootstrap()` (hub and worker). **Not** `Log.logger`: Mindustry logs chat twice from `NetClient.sendChatMessage`, and the command template closes with `&fr>` while the server's own handler appends `&fr`, so by the time a handler sees the line the id is no longer at the end of it. The formatter gets the raw arguments, where the message really does end with its id. Every string argument is checked — the test is narrow enough that ordinary log output cannot trip it, and names carry the same tag.
- The server installs its own formatter in the `ServerControl` constructor, which runs before `mods.eachClass(Mod::init)`; the wrapper captures whatever is there and delegates, so the console keeps its timestamps, colours, log file and socket output.
- The Discord side strips the same id through the same method (see Discord chat mirror) — the message is cleaned there separately, since it never passes through the log.

## Secrets file
Every credential the plugin needs lives in one `.env`-style file, `config/evict.env` (`core/io/EnvFile` + `core/io/Secrets`) — so the next one is a new key, not a new file, command or properties entry.
- **Read-only from the plugin's side**, and that is the whole point: a console command would write the value into the server log and the start script's screen log permanently, and `evict-map-generator.properties` is rewritten by the plugin and synced into worker folders. Nothing copies `evict.env` into a worker.
- Format `KEY=value` per line; `#` comments and blank lines ignored, an empty value counts as unset, an optional `export ` prefix tolerated, surrounding quotes stripped, keys matched case-insensitively.
- Missing at startup → created once as a template listing every key with an empty value (paste after the `=`), then never written again. Created with **normal permissions**, like every other config file: the server is administered remotely (FTP/panel), and a `chmod 600` file would be one the admin cannot edit. Locking it down is the operator's call.
- Keys in use: `DISCORD_CHAT_BOT_TOKEN` — one bot for the chat mirror, and the `/ban` / `/unban` slash commands (see Discord commands). Reload without a restart: `chatlog reload` or `discordcommands reload`. `VPNAPI_KEY` — the vpnapi.io key for the VPN scan (see VPN scan), optional — ip-api.com is asked without any key; `vpn reload`. The template only lists the keys that existed when the file was created, so a key added in a later version goes into an existing file by hand.
- The Discord *webhooks* (status, ban log) deliberately stay in the settings file and their console commands: a webhook URL is a per-channel capability, not an account credential, and both features are set up channel-first.

## Discord chat mirror
Hub-sent, staff-only. Operator setup walkthrough: `docs/CHATLOG_SETUP.md`. Mirrors what players do into Discord: one channel for the hub (`#hub`) and one per worker **port** (`#port-6568` …) — ports, not slots, because the channel cross-references that worker's folder and console log, like the ban log does. Sent by a **bot** (`DiscordBotChannel`, plain REST `POST /channels/<id>/messages` with an `Authorization: Bot` header — no gateway, the bot may show offline), not by webhooks: a webhook channel is capped at 30 messages/minute, a bot at 5/5 s, and the hub channel needs the sustained rate. One token plus one channel id per feed; a port without a channel simply isn't mirrored.
- **The bot creates the channels itself** (`chatlog setup <server-id>`, `DiscordGuildSetup`): a category *Evict Logs* plus `hub` and `port-<n>` for every port of the pool, adopting their ids straight from Discord's replies — no Developer Mode, no copying eleven ids, no silent typo. Needs the **Manage Channels** permission (removable afterwards). Every channel is created denying `VIEW_CHANNEL` to `@everyone` — these carry every line players type, so staff-only is set at creation rather than remembered — plus an explicit allow for the bot itself, which that deny would otherwise lock out of its own channels; afterwards you grant your staff role access. Idempotent: an existing category/channel of the same name **and type** is adopted, so re-running after raising `maxWorkers` only creates the missing ports, and a run that failed halfway keeps what it made (the ids are stored either way). Creations are paced and 429s waited out. Wiring a channel by hand (`chatlog hub <channel-id>`) stays available for a channel that already exists.
- **The token never touches the console or the settings file.** It lives in the secrets file `config/evict.env` as `DISCORD_CHAT_BOT_TOKEN=…`. A console command taking the token would write it into the server log (and the start-script's screen log) forever; the settings file is rewritten by the plugin and synced into worker folders. `chatlog reload` re-reads the file — that is also how a rotated token heals channels a 401 had disabled, without a restart. `chatlog off` drops the channels but never the secrets file (retiring a credential is the admin's call). Belt and braces: the settings sync into worker folders strips every `discord.*` key, and the secrets file is not among the files copied there at all.
- Status message and ban log stay on **webhooks** on purpose: both sit far below the webhook limits (the status edits one message twice a minute, the ban log posts only on actions), a webhook needs no credential, and the status flow is built on webhook message-edit semantics. The bot is used where a webhook cannot serve: the chat mirror needs its sustained rate.
- **What becomes a line** (positive list — nothing else ever): player chat (`Name: text`), commands as typed (`Name: /play`, including `/t` — team and ranked-spectator chat are mirrored as plain lines, no markers), `Name joined.` / `Name left.`, the hub's ban announcements, and one `🌍 New round started (seed …)` line per hub round. A message the word filter drops **is** mirrored (staff channel; the line appears followed by the ban announcement, and the detailed evidence still lives in the ban log) — only a name-banned player's join stays out (no chat line existed; the announcement carries the name). All automatic output (countdowns, captures, Extinction warnings, plugin broadcasts) stays out.
- **Lifecycle embeds** ride the same per-channel queue as the lines, so order is preserved: match start (mode + rosters) and match end (winners, losers, duration, how it ended; grey when the worker died without a result — every start embed gets its end embed) on the port channel; round end on the hub channel (winner team with 👑 leader, duration, and how: conquered every hex / `/over` / Extinction). A Ranked match's ELO movement follows the end embed as its own `📈 winner 1043 → 1067 • loser …` line once the DB write lands. The worker's own chat lines are drained one final time on worker exit, **before** the end embed, so the players' last words come first.
- **Capture** (same class both roles, only the sink differs): a chat filter registered **first**, before the word filter (logging only — the drop itself and the ranked spectator routing behave unchanged), plus `PlayerChatEvent` for registered commands — vanilla `/t` re-enters the filter chain, which would mirror hub team chat twice, so the command capture marks the player and the filter skips exactly one call. The hub queues lines directly; a worker appends them to `chat.log` (`MM-dd-yyyy HH:mm:ss<TAB>line`, console-log timestamp format) which the hub tails on the ~2 s status poll from a remembered offset (`ChatLogTail`, serialized, so poll and exit-drain can't double-read). A stale `chat.log` is deleted at spawn like the status file.
- **Delivery**: one line = one Discord message (Fish-style) at a deliberately steady **1 message/second per channel** — the bot's sustained limit (5 per 5 s) ridden evenly instead of in bursts, so the mirror never provokes 429s and a line is at most a second late. 429 + `retry_after` stays honored as the safety net; a hard rejection (bad token 401, missing access 403, deleted channel 404) marks the channel BROKEN in the checklist instead of retrying forever, and a fixed token heals it without a restart. Nothing is dropped to keep up — past the pace the queue falls behind and catches up on the next send, merging backlogged lines (beyond a 3-line backlog) into multi-line messages; embeds never merge. Only a long Discord outage can overflow the hard cap (2000/channel); the loss is counted and announced in the channel. Names/text pass `DiscordFormat` (escape + truncate + trailing-filler strip, see below) and every payload sets empty `allowed_mentions`. On shutdown a best-effort blocking flush (3 s budget) sends what is still queued.
- **Client message ids**: `DiscordFormat.sanitize` calls `core/util/MessageIdFilter.strip` (see Client message ids), so the mirror, the ban-log evidence and the status ladder all show the message without the id; on a worker it happens before `chat.log` is written.

## Discord status
Hub-only. One webhook message in a Discord channel (`#serverstatus`), edited in place every **30 s** — never a new message, and an edit notifies nobody. Two embeds: server status (player count vs. the server's slot cap, lobby/match split only while a match runs, round runtime + Extinction countdown, running matches, and a `⚠️ Restart queued` field that appears only while a restart is queued) and the top-10 ranked ELO ladder.
- Refresh is unconditional, not change-detected. The closing `Updated <t:…:R>` line is a Discord relative timestamp that counts up client-side, so a healthy server always reads "seconds ago" and a stuck one is visible by the number growing.
- Matches are identified by **pool slot** (1..`maxWorkers`), never by port, with mode label, rosters and worker uptime. Names come from the spawn-time roster (`Matches.matchStatuses()`), so a match still lists everyone after a disconnect.
- The ladder is re-queried every 5 min, and immediately whenever a stored rating changes (a ranked result or `elo`) — otherwise it would disagree with `/info` and `/top` until the slow refresh came round. The message still redraws every 30 s from the cache.
- Player names are user-controlled, so every name passes `DiscordFormat.playerName`: strip Mindustry colour tags → strip control chars → collapse whitespace → truncate to 24 → backslash-escape `\ * _ ~ ` |` (escape last, so a cut never splits an escape pair). Independently, every payload sets `allowed_mentions: {"parse": []}` — that, not the escaping, is what stops a player named `@everyone` from pinging the whole Discord server twice a minute.
- Message id is persisted (`discord.message.id`) so restarts keep editing the same message. A 404 while editing means someone deleted it → post a fresh one; a 404 while creating means the webhook is gone → stop and log. 401/403 disables; 429 backs off for `retry_after`; transient failures are logged on the 1st and then every 20th.
- Clean shutdown posts `🔴 Offline` from a JVM shutdown hook (blocking send, 3 s budget), so `restart` and normal stops are covered. A hard crash cannot reach it — that is what the counting timestamp is for.
- Transport is the JDK `java.net.http.HttpClient`: Arc's `Http` (and `HttpURLConnection` under it) has no PATCH, which Discord's message edit requires.

## Generation
Filled hexes: min 6, max 12, center bonus up to 12%; the final-seven Extinction hexes must never be filled. Chances: border 11%, second ring 3.5%, inner 1%; chain start 22%, chain continue 48%, max chain length 3.

Water: configured tries per hex (not per-core fallback); decimal tries give a fractional chance for one extra try (`4.3` = 4 tries + 30% for a fifth). Patches are noise-guided inside each hex and may share tiles with ore/oil overlays (hard-coded, no setting). Each patch has a configured percent chance to use the large tile count instead of the normal one.

## Properties-only settings (`config/evict-map-generator.properties`)

Set once, by editing the file and restarting; there is no console command for them (see `docs/CODE_RULES.md`, rule 2). `oregen` prints the build speed, `matchstatus` the duel pool.

- Ores: `ore.<copper|lead|coal|titanium|thorium|scrap>.<scale|threshold|octaves|falloff>` — applies to the next generated match.
- Water: `water.patchAttemptsPerHex`, `water.normalPatchTiles`, `water.largePatchChancePercent`, `water.largePatchTiles` — defaults `1`, `3`, `13.33`, `8`.
- Walls: `wall.fullPercent`, `wall.smallPercent`, `wall.openPercent`, `wall.passagePercent` — template percentages.
- Attrition: `attrition.core.tier1To3Percent`, `attrition.core.tier4Percent`, `attrition.core.tier5Percent`, `attrition.range.percent` (see Attrition).
- Build speed: `rules.unitBuildSpeedMultiplier` — unit-factory build speed each round; default `1.4`; copied into every worker; applies next generated match.
- Duel pool (fields of `Config`): `duel.server.ip`, `duel.server.port`, `duel.maxWorkers`, `duel.worker.map`, `duel.worker.jar` — `ip` is what clients reach workers at (blank = `/play` inert); workers use `port .. port+maxWorkers-1`. `duel.worker.map` is the Extinction map: the hub's every round and every Extinction worker host it; every other map in `config/maps` is a Pure map (see Pure matches). Defaults: ip unset, port `6568`, maxWorkers `4`, map `evict-map`, worker jar `server-release.jar`. A port outside 1–65535 or a pool size outside 1–10 is refused with a console error and the default stays.
- Ban appeal link: `moderation.banAppealUrl` — a `http(s)://` URL shown on the ban screen (a Discord invite is displayed as `discord.gg/<code>`); blank by default (plain ban screen, no appeal line); copied into every worker (see Ban screen).

## Console commands (state they save lands in the same properties file)

Every name is plain — no `evict` prefix; `banplayer` is named so because bare `ban` would replace vanilla's.

- Generator: `oregen [gen [seed] | seed <n/random> | auto on/off]` — no argument prints the generator status (auto on/off, next and last seed, build speed, terrain status and the required base-map size); `gen [seed]` generates terrain on the loaded map right now (testing only — players must reconnect); `seed` fixes the seed of the next generated map; `auto` switches generation on host (default on, not saved).
- Round: `round [time <seconds>]` — no argument prints the Fallen-team spawn assignment and the elapsed round time; `time <seconds>` sets the elapsed time.
- Match servers: `matchstatus` — the duel pool settings (`duel.*`) and the active worker servers with who is in them.
- Core cap: `corecap <n>` — adds `n` unit cap per core, live, until the server restarts; not saved.
- Ban: `banplayer <name/uuid>` — bans a stored player (online or not) by partial name or UUID, widened and logged like every other ban; ambiguous names list candidates and change nothing (see Bans).
- Word filter: `wordfilter [on/off/test <text>]` — no argument shows whether it is on, how many words it watches everywhere and how many extra are banned in names only; `on`/`off` switch it (a `Config` field, stored as `moderation.wordFilter`, default on, copied into every worker with the rest of the settings file); `test <text>` says which entry a line would trip, and whether it would ban in chat and as a name or only as a name. The words themselves are in the source, not here (see Word filter).
- VPN scan: `vpn [on/off/lock on/off/reload/test <ip>]` — no argument prints the checklist (on/off; one line per source: how it is set up — key loaded / not set / rejected — today's lookups against its cap, a pause, its last error; whether hits reach the ban log or only the console; today's cache answers, hits, clean, skipped; the cache size; and the lock: on/off, how many accounts are locked and verified); `on`/`off` switch the scan (stored as `moderation.vpnScan`, default on — runs on ip-api alone without a vpnapi key); `lock on`/`lock off` switch the lock decision (stored as `moderation.vpnLock`, default on; see VPN lock); `reload` re-reads `config/evict.env`; `test <ip>` looks one address up at every source right now (it counts against the day), says what each answered and whether a join from it would be written down, and posts that verdict into the ban-log channel as a test line. Hub only.
- Free: `free [name/uuid]` — no argument lists the locked accounts (name, UUID, address, reason); a UUID or a part of a name that matches exactly one frees it (several matches are listed and nothing happens). Hub only; see VPN lock.
- Ban log: `banlog [url/off/test]` — no argument reports the wiring (queue length, last success/error); a webhook URL adopts it; `off` stops logging; `test` posts a sample entry. Stored as `discord.banlog.webhook.url`. Point it at a staff-only channel — entries contain IPs.
- Discord commands: `discordcommands [setup | role <name> | reload | off]` — no argument prints the checklist (token loaded, server, role, connection state, whether the commands registered). `setup` needs **no ids at all**: it asks Discord which server the bot is in (`GET /users/@me/guilds`), adopts it when there is exactly one, registers the commands, connects, and lists the server's roles by name; several servers → it prints them and waits for `discordcommands <server-id>`. `role <name or id>` sets who may use them, by role **name**, so Developer Mode is never needed. `reload` re-reads `config/evict.env` after a token rotation; `off` stops answering (the commands stay visible in Discord until Discord drops them). Stored as `discord.commands.guild` + `discord.commands.role`; never copied into worker folders. There is deliberately **no** command that takes the token — typing it would log it (see Secrets file).
- Chat mirror: `chatlog` — no argument prints the checklist (token file loaded or not, hub + every port of the current pool, wired or not, plus orphaned ports outside the range after a `basePort` change); `chatlog setup <server-id>` has the bot create and wire every channel (needs Manage Channels; idempotent — see Discord chat mirror) **and** wires `/ban` + `/unban` to the same server if they are not already (see Discord commands); `chatlog hub <channel-id>` / `chatlog <port> <channel-id>` wire one feed by hand (`… off` unwires it; channel ids via Discord Developer Mode → Copy Channel ID); `chatlog reload` re-reads `config/evict.env`; `chatlog off` drops every channel (never the secrets file); `chatlog test` posts a test line into every configured channel, so of eleven pasted ids the wrong one shows up as the channel that stays quiet. There is deliberately **no** command that takes the token — typing it would log it (see Secrets file); `chatlog token …` only says so. Channel ids stored as `discord.chatlog.hub.channel` + `discord.chatlog.port.<port>.channel`; never copied into worker folders. Staff-only channels — they mirror everything players say.
- Discord status: `discordstatus [url/off/test]` — no argument reports the current wiring (message id, last success, last error); a webhook URL adopts it and posts a fresh message; `off` posts Offline and stops; `test` refreshes immediately. Stored as `discord.webhook.url` + `discord.message.id`; changing the URL clears the id. Setup is Discord-side: create the channel, Integrations → Create Webhook, paste the URL.
- Player data: `playerinfo [name/uuid]` (single match also prints lastIP + all known IPs from Mindustry's admin store, for `ban ip`), `elo <name/uuid> <value>` (see Player data above).
- Restart: `restart` queues a graceful update restart (fires when no worker runs and the round ends / hub is empty / round is < 10 min old after a 30 s on-screen countdown); the hub-empty condition is re-checked every tick while a restart is queued and fires after the hub has been empty for 10 uninterrupted seconds, so a queued restart no longer has to wait out a long round nobody is playing; `restart cancel` drops it, also mid-countdown (hides the HUD, announces the cancel); `restart now` shows a 10 s countdown, then exits. Countdowns tick per second in a HUD popup (3 s popup lifetime) and post milestone seconds to chat (every 10 s plus the last five). The exit closes the network, then hard-exits via `System.exit(0)` (the duel-worker way; shutdown hooks still flush the player DB), with a 10 s `Runtime.halt(0)` guard should a shutdown hook ever wedge; the external start-script loop relaunches the server.

## Safety notes

- No large one-tick network bursts; never send thousands of `setFloorNet` packets in one tick — terrain floor changes stay throttled.
- Extinction removes logical ownership, cores, buildings and units immediately; only the visual terrain conversion streams gradually.
- Preserve the double-wipe capture protection.
